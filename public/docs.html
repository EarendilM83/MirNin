MirNin Monitor — Documentation

One page for everyone: what the monitor is, how to read it, how to run it, and how it works under the hood.

Part 1 · For everyone

What is this?

MirNin Monitor answers one question, continuously: “Is our platform working right now, for people in the countries we serve?”

A website can be perfectly fine in Tbilisi and broken in São Paulo — or, more subtly, fine on one Georgian internet provider and blocked on another. The monitor checks our URLs every few minutes from real machines in those countries and networks, and shows the results as a wall of live tiles — like participants in a video call, one tile per country. Green wall = all good. Anything else tells you exactly where and what.

You don't need an account or any technical knowledge to read it. If the dashboard asks for a password, ask the admin who runs it.

Reading the dashboard

  • Sidebar on the left — everything is organized as projects → categories → URLs (e.g. FortuneJack → Payments → cashier page). Every level carries a colored dot showing the worst status inside it, so bad news is visible even on collapsed items. All projects at the top shows one summary card per project; click anything to drill in, and the breadcrumb above the content always shows where you are. Press ⌘K (Ctrl+K) to jump to any project, category, or URL by name.
  • Dashboard / Statistics — the two lenses at the top right apply to whatever the sidebar has selected: pick a project, and both the dashboard and the statistics show only that project.
  • Summary strip — how many probes are green / yellow / red right now, and the median response time.
  • Tiles — each tile is one location watching one URL: country flag and name (plus provider, if pinned), the latest response time in milliseconds, a status label, a small graph of recent checks, uptime for the last 24 hours, and the time of the last check. Red or yellow tiles also show the error in plain text.
  • Yellow banner “Suspected ISP-level block” — providers inside one country disagree: e.g. Magti users can't reach us while Silknet users can. This is a strong, specific signal — see the playbook below.
  • Recent incidents (bottom of each target tab) — outages as a story: when each started, how long it lasted, which location, what failed.
  • Click any tile to pin it large (like pinning a speaker in a call): full history graph, a week-at-a-glance heatmap, recent checks, and — during an outage — the automatic diagnosis.
  • Grid / List switch (top right) — the same data as tiles or as a dense table.

The four statuses

StatusMeaningGut reaction
Operational The site answered normally and fast enough. All good.
Degraded The site answered, but slowly or with a client error — users there are having a worse experience than usual. Keep an eye on it; escalate if it persists.
Down No usable answer: timeout, connection failure, server error — or the page came back without our expected content (typically a block page pretending to be us). Real problem for users in that location. Act.
No data The check itself couldn't run (probe network unavailable). We don't know the site's state from that location. Not evidence of an outage — but also not proof of health.
“No data” is deliberately different from “Down”. We couldn't look is not the same as the site is broken — the monitor never guesses.

What to do when…

  • One country is red, the rest are green — a regional problem: routing, a CDN edge, or geo-blocking. Open the tile: the diagnosis says whether it's DNS, the network path, or the website itself. Share that screenshot with engineering.
  • One provider is red inside a green country (the “ISP split” banner) — users on that provider (e.g. Magti) can't reach us while others can. The pinned tile's diagnosis usually shows the pattern “DNS fine, ping dropped, content intercepted”, which is evidence of in-network filtering — exactly what you need when contacting the ISP or the regulator.
  • Everything is red at once — either the platform itself is down (check with engineering first) or, if statuses read “No data”, the monitor lost its probe network — an admin should check the Settings and the notice in the header.
  • A tile is yellow with a high ms number — slow, not broken. If it's one distant country and it's business-critical there, that's a case for a CDN/edge conversation, backed by the p95 numbers in the pinned view.
  • “cert expires in N d” badge — our security certificate is about to expire; if it does, browsers will scare users away. Tell engineering — it's a ten-minute fix before the deadline and an outage after it.

Statistics & reports

The Statistics tab merges every target and location into one picture:

  • Headline cards — overall uptime for 24 h / 7 d / 30 d, total checks, incident count, and average repair time (how long outages take to resolve).
  • The year at a glance — a GitHub-style calendar: one square per day. Green = clean day, yellow = brief issues or degradation, red = real downtime (≥ 1% of that day's checks failed), gray = no data yet. Hover any square for the numbers. Daily statistics are kept forever, so this becomes the long-term memory of the platform.
  • By country / by target — 30-day uptime, average latency, and incident counts, sorted worst-first so problems float to the top.
  • Download a report — pick the data (check summaries, incidents, or raw checks), granularity (daily/hourly), a date range, and optionally specific targets and countries; preview the result, then download as CSV (opens in Excel/Sheets) or JSON. Filters compose freely — e.g. “incidents in Georgia, last quarter” or “daily uptime for the payments API, all countries, June”.
Part 2 · For admins

Projects, categories & status rules

Projects group what you monitor by product or brand; categories group URLs inside a project (Core pages, Payments, Promo campaigns…). Create them from the sidebar (“+ New project”, “+ category”); a URL's category is picked in its edit form. Each project can have its own alert webhook — its alerts go to that channel, prefixed [Project · Category], others fall back to the global webhook. Empty categories and projects can be deleted; non-empty ones are protected.

Status rules define what Operational / Degraded / Down mean. Global defaults live in Settings → “Status rules”; any URL can override individual fields in its edit form (empty field = inherit, shown in gray). The rules cover: which HTTP codes count as passed or degraded, a “Treat 403 as reachable” shortcut for WAFs that block monitoring probes, the latency threshold — fixed, or adaptive (“slower than N× this location's own 7-day baseline”, so Brazil isn't judged by Frankfurt's standards) — the timeout, and whether a failed content assertion means Down, Degraded, or is ignored. The “Preview against last 24 h” button re-classifies real stored checks under your draft rules before you save, so you can see the effect immediately. When rules change, the recent (~48 h) history is re-classified; older aggregates keep their original classification.

Adding a URL to watch

Click + Add URL (top right).

Give it a name people recognize (“Main site”, “Payments API”) and the exact URL — a lightweight page like /health is ideal, but any page works.

Pick how often to check. 1–5 minutes is right for most things; every 30 s only for the truly critical (and mind probe-network rate limits).

Choose locations — see the next section.

Optionally set Expect text: a word or phrase that is always on the real page (e.g. the product name). If a response comes back without it, the check counts as Down even when the status code looks fine — this is what unmasks ISP block pages that return a fake “successful” page.

Save. Checks start within seconds; the tab appears immediately.

Each target tab has Check now (run immediately), Pause/Resume, and Edit (which also contains Delete).

Countries & providers

A location is a country, optionally pinned to a provider (ISP). Three patterns:

  • Country only (“Germany · any provider”) — a probe somewhere in that country. The default, right for most countries.
  • Country + provider — add the same country several times with different providers (Georgia · Magti, Georgia · Silknet) to detect provider-level blocks. When you focus the provider field, the form shows which providers currently have live probes in that country — pick from those chips rather than guessing.
  • This server — checks run directly from the machine hosting the monitor. Works for internal URLs the public probe network can't reach.
Probe availability is live, not guaranteed: providers appear in the hint only while someone hosts a probe there. If a pinned provider has no probe online, its tile shows “No data” until one returns.

The focus view

Click a tile to pin it. Beyond the big graph you get:

  • Time ranges — 1 h / 6 h / 24 h use raw checks; 7 d / 30 d switch to hourly aggregates. Uptime for 24 h and 30 d is shown alongside.
  • Latency anatomy — the colored bar splits the last response into DNS → Connect → TLS → First byte → Download. A slow “First byte” is our server thinking; slow “Connect/TLS” is network distance; slow “DNS” is name resolution.
  • Week heatmap — 7 days × 24 hours; spot patterns like “degrades every evening at peak time”.
  • Automatic diagnosis — when a location goes down, the monitor immediately runs ping + DNS from that same location and writes a verdict, e.g. “DNS is clean but the network path drops traffic — points at routing or in-network filtering, not your server.”
  • Served by — which CDN edge answered, response size, redirects, and days until the TLS certificate expires.

Alerts

Configure once in Settings: paste a webhook URL (a Slack incoming webhook works as-is), choose how many consecutive failures trigger an alert (default 2 — a single blip stays quiet), and press Send test alert to confirm delivery.

Then the monitor messages you like this:

🔴 MirNin platform is DOWN from GE · MagtiCom — expected content not
   found in response (3 consecutive checks, since 12:36)
   Diagnosis: DNS resolves correctly but ICMP is dropped and HTTP is
   intercepted — consistent with in-network filtering.

🟢 Recovered: MirNin platform from GE · MagtiCom after 41 m.

Down-alerts include the diagnosis when it's ready; recovery messages include the outage duration. Alerts can be disabled globally with one checkbox.

Settings & login

  • Password — the deployment sets ADMIN_PASSWORD; everyone then signs in with it (sessions last 7 days). Without it the dashboard is open and shows an “Unprotected” notice — acceptable on a laptop, not on a server.
  • Globalping token — Settings → paste the API token from globalping.io (free account). It raises the checks-per-hour limit substantially; sponsoring the project adds credits beyond that. Without a token, heavy schedules can hit rate limits and tiles temporarily show “No data”.
  • Probes selector (header) — “Real” uses the live probe network; “Simulated” generates synthetic results so you can demo or explore the UI without network access. Simulated data is clearly marked and never mixes into real history unnoticed — switch back to Real for actual monitoring.
Part 3 · Technical

Architecture

A single zero-dependency Node.js process (≥ 18.17) serves the dashboard, runs the scheduler, talks to probe providers, and persists everything as JSON. No database server, no build step, no npm packages.

Browser dashboardpublic/ · vanilla JS, no framework
REST + Server-Sent Events (live updates) ↕
server.jsHTTP · auth · API · SSE · static
scheduler.jsper-target intervals, no overlap, incident tracking triggers
checker.jsproviders, classification, diagnostics
store.jsconfig, raw results, rollups, incidents
alerts.jswebhook down/recovery messages
outbound only ↓
Globalping APIreal probes per country/ISP: http, ping, dns
Local checksnode:http(s) from this machine, phase timings
Simulatedsynthetic provider for demos
Alert webhookSlack-compatible {"text"} POST

Check lifecycle: the scheduler ticks every second; a due target fans out to all its locations (one Globalping measurement covers all remote locations; local locations are fetched directly with per-phase socket timing). Each result is classified (up / degraded / down / unknown), appended to raw history, folded into the current hourly rollup, and evaluated against incidents: a transition to down opens an incident and fires ping + DNS diagnostics from the same location; recovery closes it. Every result is broadcast over SSE so open dashboards update without polling. Alerts fire when an incident reaches the configured consecutive-failure threshold, and again on recovery.

Status classification: network failure, timeout, HTTP 5xx, or a failed content assertion → down; HTTP 4xx or latency above the target's threshold → degraded; a check that could not run (probe network unreachable, no probe in the pinned network) → unknown, excluded from uptime math.

Security model: optional password gate over everything except /api/healthz and the static files; sessions are HMAC-signed expiry cookies (secret generated once, stored under data/ with mode 600); the Globalping token is stored server-side and echoed to the UI only masked; all user strings are HTML-escaped in the frontend.

Everything flushes to disk every 30 s and on shutdown; the process recovers its full state on restart. Uptime is computed from rollups as the share of non-down checks among known checks (unknown excluded from the denominator).

Deployment

# Docker (recommended — any $5 VPS)
ADMIN_PASSWORD=change-me docker compose up -d --build

# Bare Node (18.17+), no dependencies to install
ADMIN_PASSWORD=change-me npm start        # → http://localhost:4000

ADMIN_PASSWORD–Enables the login gate — always set it on a server
GLOBALPING_TOKEN–Probe-network token (Settings UI overrides)

Who watches the watcher: point a free external uptime service at /api/healthz. If the monitor's own host dies, nothing else will tell you.

Rate limits: one check of one URL from one location = one probe test. Budget: locations × (3600 / interval) tests per hour per target. Unregistered ≈ 250/h, registered (free token) ≈ 500/h, sponsorship credits go beyond. “This server” and Simulated checks are always free and unlimited.

Glossary

ProbeA real machine in some country/network that performs a check on our behalf.
TargetA URL we monitor, with its schedule and locations.
LocationCountry + optional provider a target is checked from. One tile per location.
Latency / msHow long the site took to answer, in milliseconds. Under ~300 ms feels instant; multiple seconds feels broken.
p95The response time 95% of checks beat — the “bad day” number, more honest than the average.
UptimeShare of checks (in a window) that were not Down. 99.9% ≈ 43 minutes of downtime per month.
DNSThe internet's phone book: turning our domain name into a server address. If DNS fails, users can't even start loading the site.
TLS / certificateThe encryption handshake behind the padlock icon. An expired certificate makes browsers block the site with a warning.
CDN edgeThe nearby datacenter that serves our content in each region. “Served by” on a tile names it.
ISP / providerAn internet provider (Magti, Silknet…). Blocks and outages often happen per-provider, not per-country.
Content assertionText that must appear in the response for the check to pass — unmasks block pages that fake a successful response.
IncidentA group of consecutive failed checks from one location: start, duration, error, diagnosis.
WebhookA URL that receives our alert messages — e.g. a Slack channel's incoming-webhook address.
